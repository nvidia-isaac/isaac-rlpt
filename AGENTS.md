# AGENTS.md

Guidance for AI agents (and humans) working in `isaac_rl_posttraining`.

## Overview

This repo post-trains robot policies with reinforcement learning.
The main method is **DSRL**: a SAC agent learns to steer the flow-matching noise of a **frozen** vision-language-action policy (e.g. GR00T-N1.7 or pi0), raising its success rate on a task without touching the base model's weights.
It runs across pluggable simulators (a Unitree-G1 humanoid in IsaacLab-Arena, LIBERO, and Isaac Lab 3.0 tasks).
The core library is simulator-agnostic; simulators, frozen policies, and RL algorithms all plug in through small registries.

## Codebase map

**`isaac_rl_posttraining/`** — the core library. It never imports a simulator (see Invariants).
- `algorithms/` — the RL methods. `sac/` is the DSRL learner; `iql/` and `sft/` fine-tune a trainable base model offline from demonstrations; `dsrl/` wires up the steering; `ppo/` is the on-policy learner and controller used to fine-tune GR00T through the runtimes; `base.py` is the shared contract; `replay_learner.py` hosts an off-policy algorithm behind the learner contract and packs the controller-drawn replay batches it consumes; `ppo/ppo.py` is the `PPO` algorithm object the on-policy loop drives (GAE batches on the controller, the clipped-update learner on the ranks).
- `policies/` — the **frozen base policies** that get steered, behind one uniform `BaseModelPolicy` contract. `gr00t/`, `pi0/`, `dreamzero/` (an in-process steerable `local_base_model.py` plus a served native-only `server_base_model.py`), plus a `Mock` in `base.py`. Each has a `base_model.py` with a `from_dsrl_config` factory. For PPO fine-tuning the same names select a **trainable adapter**: `trainable.py` holds the `TrainablePolicy` contract, the `TrainablePolicySpec` loading recipe and the adapter registry; `flow_sde.py` the shared flow-SDE sampling, likelihood and value head; `gr00t/flow_sde.py` (N1.5), `gr00t/flow_sde_n17.py` (N1.7) and `pi0/flow_sde.py` (pi0, experimental) the per-base-model adapters; `gr00t/flow_sde_policy.py` the rollout-worker policy that drives any of them.
- `envs/` — the environment layer and the transport to a running simulator. `transport.py` / `zmq_transport.py` are the wire protocol (kept dependency-light — see Invariants); `providers.py` holds the simulator registry (`_PROVIDERS`, `_ENV_BUILDERS`); `steering_wrappers.py`, `action_wrappers.py`, `obs_wrappers.py`, `dino_wrapper.py`, `language_wrappers.py` shape observations/actions; `vector_backends.py` gives sync/async/batched vector envs; `embodiments/` holds the `DatasetAdapter` registry (`_ADAPTERS`); `simulator_entry.py` defines `SimulatorEntry`, the class a simulator or robot subclasses to plug into the runtime layer (`make_environment` on the worker, worker layout, evaluation mode; two required members, defaults for the rest) without the core importing it; an entry that declares `observation_spec` / `action_spec` from an `Observation` subclass gets the launch-time check in `runners/spec_checks.py` and a `steering_key_mapping` derived from the declaration.
- `training/` — the training loops and what they share: `off_policy.py` (`OffPolicyTrainer`: replay buffer, bursts of updates per collected decision), `on_policy.py` (`OnPolicyTrainer`: iterations of fresh episodes over a pluggable `OnPolicyAlgorithm`; its config in `on_policy_config.py`), `offline.py` (the IQL/SFT demonstration sources), `checkpoints.py` (`CheckpointStore`, `FingerprintSink`), `evaluation.py` (`RolloutEvaluator` scores policy states on a rollout group), `data_source.py` (every training round of every loop: lineage, telemetry, optional saving, and the replay buffer when there is one), `trajectories.py` (`ChunkTrajectory`, the on-policy view of collected episodes).
- `rollouts/` — what the rollout workers share: `action_chunk.py` (the decision record), `steering_step.py` (the steering decision step), `episode_tracker.py` (per-environment episode accounting), `transition_sink.py` (the replay write seam), `video.py` (stacks camera frames and writes the evaluation MP4).
- `policies/feature_cache.py` — cached activations of frozen sub-modules (`FeatureCaching` protocol, pack/unpack helpers); carried by `Transition.policy_outputs.features`, stored by replay buffers, consumed by learners instead of recomputation.
- `runtimes/` — where rollout workers and distributed learners run: `native.py` (in-process), `rlinf/` (Ray-placed workers, GR00T policy servers and FSDP learner groups over the RLinf scheduler); `base.py` and `learner.py` hold the provider-neutral contracts; `gym_worker.py` (one unbatched env per worker: `GymRolloutWorker` built from a `GymWorkerSpec`, `SparseOutcomeReward`, worker-count resolution) and `batched_worker.py` (one natively batched simulator per worker, `BatchedWorkerSpec`) are the portable rollout workers; construction recipes are picklable `*Spec` dataclasses the runtime calls with a worker's context; `policy.py` is the acting-policy contract a worker drives (`ActionChunkPolicy`, with a per-decision `DecisionMode` of warm-up, train or eval); `steering_policy.py` builds the steering actor + frozen decoder a worker runs and `edit_policy.py` the reference-edit actor over the frozen reference decode; `steering_rollouts.py` composes a simulator entry and a steering policy into the rollout worker spec of one phase; `policy_families.py` routes an algorithm family (steering or edit) to its policy, reward and update credit; `policy_snapshot.py` moves policy states to and from torch and snapshot files; `concurrency.py` wraps calls for overlapped collection; see `docs/runtimes.md`. Provider SDKs are imported only when a runtime is opened.
- `runners/` — `build.py` turns a composed config into a run (`build_run`, the launch plan the dry run prints) and dispatches on the algorithm's family; `off_policy_launch.py`, `dsrl_ppo_launch.py`, `flow_sde_ppo_launch.py` and `offline_launch.py` build one family each; `off_policy_models.py` builds the environment stand-in and networks of each off-policy paradigm (latent steering, residual flow steering, direct action); `simulator_entries.py` resolves the simulator entry a composed config runs on and describes one phase's environments and server address.
- `data/` — the typed records every layer exchanges (`Observation`, `LearnerAction`, `EnvAction`, `Transition`, `Episode`, their specs and the checker); see `docs/data_model.md`.
- `buffers/` — replay: `replay.py` is the one `ReplayBuffer` (episode-organized, typed transitions, whole-episode eviction, sample-time reward channels), `samplers.py` the samplers learners draw through (`UniformSampler`, `SuccessFractionSampler`, `MixedSampler`, `SequenceSampler`; `buffer.success_fraction`, `buffer.demonstrations`), `storage.py` its saved directory format. `modules/` — network building blocks (`mlp`, `cnn`, `rnn`, `transformer`).
- `configs/` — the Hydra config. `train.yaml` is the one root config; `schema.py` is the dataclass schema and defaults (`base_model_schema.py` holds the `base_model` group's); `registry.py` populates the Hydra ConfigStore; `algorithm/` (one option per method, each declaring its `name` and `family`), `base_model/`, `runtime/`, `policy/`, `value_function/` are config groups.
- `utils/`, `loggers/` (wandb), `compat/` (optional third-party adapters).

**`simulators/`** — self-contained simulator integrations, one directory each.
- `g1_arena/` — the reference (validated) integration: Unitree-G1 whole-body control in IsaacLab-Arena. `env.py` is the Gymnasium client over the transport; `runtime.py` is the `G1Arena` entry; `env_server.py` is the sim-side server (runs under the isaac-sim python); `embodiment.py` is the `g1_wbc` dataset adapter; `configs/simulator/g1_arena.yaml`; `patches/`; `tests/`; `README.md`; the launchers and the GR00T modality configs live in `example_workflows/g1_arena_posttraining/`.
- `libero/` — LIBERO (validated). `env.py`, `policies/` (pi0/gr00t on LIBERO), `runtime.py` (the `Libero`, `LiberoPi0` and `LiberoDreamZero` entries, one per base-policy convention), `configs/`, `tests/`, `README.md`; the launchers live in `example_workflows/libero_posttraining/`.
- `isaaclab/` — Isaac Lab 3.0 manager-based tasks stepped in-process (validated on Franka cube stacking). `env.py` (task mappings, single and batched views), `subprocess_env.py` (a simulation served from a child process), `runtime.py` (the `IsaacLab` entry: one scene per worker for the steering families, all of a worker's scenes for the GR00T flow-SDE policy in `isaac_rl_posttraining/policies/gr00t/flow_sde_policy.py`), `configs/`, `tests/`, `README.md`.
- `robolab/` — a DROID integration marked **⚠️ experimental** (single-env, no reproduction suite); it carries its own `runtime/`, policy adapters and docs.
- `_template/` — a seven-joint stand-in robot (`env.py`, `runtime.py`) that passes the dry run and trains on CPU through `+simulator.entry=simulators._template.runtime:MyRobot`; the starting point for a new simulator, run end to end by `tests/integration/test_out_of_tree_entry_launch.py`.

**`example_workflows/`** — runnable workflows built on the library, one folder each, and the home of new research (real+sim co-training, world-model transfer, video-to-data, ...). Each folder follows `example_workflows/_template/`: a README with a fixed section order, a `smoke.sh` that runs in under two minutes without a GPU or external repository, `results/results.json` with every reported number and its provenance (rendered into the README by `example_workflows/_common/results_table.py`), and an `internal/` directory for everything that only works inside the company. `_common/` holds the shared helpers (evaluation protocol, results table, smoke runner, the `internal/` policy). `example_workflows/MIGRATION.md` is the checklist for moving an existing example in.
**`tools/`** — repository tooling that is not a launcher: `strip_internal.py` removes every `internal/` directory of the repository and the internal-only paths in `release.INTERNAL_ONLY_PATHS` (the internal CI files and the release skill) for a release; the internal repository also carries the tool and the contributor skill that build a release branch from one of its revisions, both stripped by it.
**`scripts/train.py`** — the one Hydra entry point every launcher invokes (`algorithm=dsrl_sac|rfs|sac_edit|ppo|dsrl_ppo|iql|sft`); `scripts/ppo/` holds the retired PPO entries, which forward to it for one release.
**`docs/`** — the documentation site (`docs/README.md` builds it). `docs/pages/` is the user-facing guide: installation, workflows, algorithms, the command-line reference and the `extending/` recipes. The top-level `docs/*.md` files are the developer reference: `base_models.md`, `data_model.md`, `dsrl.md`, `infrastructure.md`, `runtimes.md`, `ppo.md`, `iql.md`, `sft.md`, `runtime-class-interactions.md`, `adding_a_base_model.md`, `adding_an_algorithm.md`. A `docs/<name>/` folder with its own `index.html` is a project page, a self-contained static site the docs workflow serves at `/<name>/` beside the documentation.
**`tests/`** — `unit/` (simulator-independent) and `integration/`; each simulator additionally has its own `tests/`.
**`skills/`** — the customer-facing agent skills (`isaac-rlpt-add-simulator`, `isaac-rlpt-add-base-model`, `isaac-rlpt-add-algorithm`), each with `SKILL.md`, `evals/evals.json` and `BENCHMARK.md`; `.agents/contributor-skills/` holds the contributor-only ones (`isaac-rlpt-audit-repo`). `.claude/skills/` and `.codex/skills/` are symlinks into these, so there is one copy.

## Run flow

A workflow launcher (`example_workflows/<workflow>/scripts/train.sh`) boots the simulator's env-server(s) and the learner (`scripts/train.py algorithm=<name>`).
`train.yaml` composes one `algorithm:`, `simulator:`, `base_model:` and `runtime:` group; `runners/build.py` prints the launch plan and dispatches on the algorithm's `family`.
For the steering and edit families, `build_base_model` looks the frozen policy up in the base model registry and builds it, `setup_dsrl_env` builds one local environment that sizes the models, and the off-policy loop trains the actor on the runtime layer: rollout workers collect through the simulator's registered entry (`envs/simulator_entry.py`), the learner trains in this process, and a rollout evaluator scores the published weights every few thousand steps.
The on-policy family (`ppo`, `dsrl_ppo`) opens a learner group and rollout workers on the selected runtime and runs `OnPolicyTrainer` with the `PPO` algorithm object.

## Extending it — the plug-in seam

Adding a piece means adding one registry entry in the shape of its siblings, not editing a dispatch chain.
- **A simulator or robot**: a `class MyRobot(SimulatorEntry)` in `simulators/<name>/runtime.py` with `name` and `make_environment` (the base class defaults the rest: one environment per worker, shared evaluation, any base model, conventional observation keys; override what differs; declare `observation_spec` / `action_spec` from an `Observation` subclass, see `docs/data_model.md`, and the launch plan checks the policy against the simulator and derives the steering key mapping), registered in `_SIMULATOR_ENTRIES` next to `_PROVIDERS` / `_ENV_BUILDERS` in `envs/providers.py` (keyed by the simulator segment of `env_name`, matched exactly) or attached per run with `+simulator.entry=<module>:<Class>`; a `DatasetAdapter` in `envs/embodiments/` if the base model needs one; a `configs/simulator/<name>.yaml`. Start from the stand-in package `simulators/_template/`. Load the `isaac-rlpt-add-simulator` skill (`skills/isaac-rlpt-add-simulator/`) for any custom simulator, robot or env-server task and for a `SpecMismatch`, missing-entry, episode-cap or server-address error on one; `docs/pages/extending/add_a_simulator.md` is the full guide.
- **A base model**: add `policies/<name>/base_model.py` with a `from_dsrl_config`, call `register_base_model(...)` in `policies/__init__.py`, add `configs/base_model/<name>.yaml`. Load the `isaac-rlpt-add-base-model` skill (`skills/isaac-rlpt-add-base-model/`); `docs/pages/extending/add_a_base_model.md` is the full guide. To fine-tune it with PPO as well, subclass `FlowSDEActorCritic` (`policies/flow_sde.py`) and register the adapter in `policies/trainable.py` (the guide's "Fine-tuning adapter (optional)" section).
- **An RL algorithm**: add `algorithms/<name>/`, register it in `algorithms/registry.py`, and add `configs/algorithm/<name>.yaml` declaring its `name` and `family`. Load the `isaac-rlpt-add-algorithm` skill (`skills/isaac-rlpt-add-algorithm/`); `docs/pages/extending/add_an_algorithm.md` is the full guide.

## Invariants (guardrails, with the test that enforces each)

- The core (`isaac_rl_posttraining/`) imports **zero simulators** — simulators depend on core, never the reverse. (`tests/unit/test_repo_hygiene.py`)
- The GR00T policy is **embodiment-agnostic** — it never imports the env layer or names a specific simulator; the launcher resolves the embodiment adapter and passes it in. (`tests/unit/test_gr00t_embodiment_layering.py`)
- `envs/transport.py` and `envs/zmq_transport.py` stay **loguru- and torch-free** — the sim-side env-server imports them under the minimal isaac-sim python. Use `print(flush=True)` for their few diagnostics; a `from loguru import logger` there breaks every simulator run.
- Every path a doc mentions must resolve. (`tests/unit/test_doc_references.py`)
- Each agent skill has one copy, under `skills/` or `.agents/contributor-skills/`; `.claude/skills/` and `.codex/skills/` hold only symlinks to them, and every skill carries `evals/evals.json` and `BENCHMARK.md`. (`tests/unit/test_skills.py`)
- No internal codename leaks into the source. (`test_repo_hygiene.py`)
- Under `example_workflows/`, anything that only works inside the company (cluster scheduler, container registry, object-store and shared-filesystem paths, internal hosts) lives under an `internal/` directory, and nothing outside those directories references it, so `tools/strip_internal.py` leaves a working tree at release. Every workflow folder has the template's files and its README results table matches its `results/results.json`. (`tests/unit/test_example_workflows.py`)

## Working in the repo

- The environment comes from `uv.lock`: `uv sync` once, then prefix commands with `uv run`. Run the CPU-safe tests: `uv run pytest tests/ simulators/*/tests/ example_workflows/*/tests/ -m "not gpu and not arena and not libero and not slow"`. Run every workflow's smoke check: `uv run python -m example_workflows._common.smoke`. The `gpu` / `arena` / `libero` markers need hardware or a simulator and skip cleanly; `slow` is long-running.
- Launch training: `example_workflows/<workflow>/scripts/train.sh <TASK> [hydra overrides]` with `POSTTRAIN_BASE_CKPT` and `ISAACLAB_ARENA_PATH` set, plus `POSTTRAIN_DATA_ROOT` for the offline algorithms (`ALGO=<name>` picks the algorithm); `python scripts/train.py algorithm=<name> ...` is the launcher-free form. `TRAIN_SIM_DEVICE=cpu` runs physics on CPU. `ISAAC_RL_POSTTRAINING_DRYRUN=1` prints the resolved launch plan and exits.
- Naming: `POSTTRAIN_*` are pipeline-level environment variables (checkpoint, data root); `DSRL_*` are the steering algorithm's own knobs. `steering_key_mapping` is the observation-key contract: every simulator env exposes it as an attribute, and the entry's method of the same name derives it from the declared observation (or returns the conventional keys).

## DO NOT

- **Don't leak task or conversation provenance into comments.** Don't narrate why you were asked to make a change — no branch/parity references ("keep parity with develop"), no task echoes ("deprecated as requested"), no back-and-forth context. That belongs in the commit message or MR. Genuine design rationale — the non-obvious reason the code is shaped the way it is — *does* belong in a comment.
- **Don't carry dead code.** When porting or refactoring, bring over only what is actually reachable, and clean it as you go. Don't copy hacks, unused paths, stale comments, or byte-parity scaffolding.
- **Don't use fallback defaults for required values.** For required config, inputs, and invariants, access the value directly or validate it once up front, then raise with a clear error if it is missing or invalid. Avoid `dict.get(k, default)`, `getattr(o, a, default)`, `x or fallback`, and broad `try/except` when the fallback would hide a misconfiguration. Defaults are fine only for genuinely optional, documented behavior.
- **Don't add defensive checks that hide bugs.** Don't guard with `hasattr`, `getattr`, `try/except`, or a silent fallback around an attribute or call that should always be present — access it directly and let it fail loudly. Reserve existence checks for genuinely optional attributes, duck-typed interfaces, or compatibility boundaries.
- **Don't use a catch-all branch for a known set of modes.** Give each real mode its own explicit condition. Reserve `else` / default cases for the genuinely unexpected, and make them raise with a clear error. A real mode written as the fallback silently swallows unspecified or invalid input.
- **Don't write vague or unnecessarily stringized type hints.** Parameterize containers: `dict[str, Tensor]`, not bare `dict` / `list`. Don't use `object` or `Any` to dodge the real type. Don't quote annotations that don't need it — use imported types unquoted, reserving string / forward-ref annotations for genuine forward references and `TYPE_CHECKING`-only imports. Use built-in generics and `|` unions: `list[int]`, `str | None`, not `typing.List`, `Dict`, `Optional`, or `Union`.
- **Don't overdo inline loops and conditionals.** Collapse multiple comprehensions over the same iterable into one explicit `for` loop — one pass, readable. Use a multi-line `if` / `else` instead of dense or nested ternaries. A single simple comprehension or ternary is fine; reach for the explicit form once expressions stack up or nest.
- **Don't carry conditions an enclosing guard already guarantees.** Validate the invariant up front, then rely on it. `x and not y` inside `if x:` is just `not y`. Gate on one clear flag, not a disjunction of overlapping ones.
- **Don't reach into another object's private internals.** Go through its public API. Don't read or mutate `_`-prefixed attributes from outside, and don't address them by hardcoded private names. If the operation you need doesn't exist, add a method to that class instead of reaching in.
- **Don't bundle unrelated responsibilities into one function.** Split distinct concerns into separate units, but don't fragment one coherent operation just to make it shorter.
- **Don't embed one language inside another.** A non-trivial script of one language — a multi-line Python heredoc in a shell script, a long SQL/HTML string built by concatenation — belongs in its own lintable, testable file that you call, not inlined as a blob. Short one-liners (`python3 -c '…'`, a one-line `awk`) are fine.
- **Don't edit generated or vendored code by hand.** Do not modify generated files, vendored dependencies, lockfiles, or large snapshots unless the task requires it. Change the source of generation instead, and regenerate.

## Coding principles

- **Fail loud, never silent.** If a required value is missing or a config is wrong, raise immediately with a clear message. Never substitute a default that masks a misconfiguration or silently produce a wrong result. Validate at construction/build time, not deep in a hot path — a silently wrong config can cost days of GPU time, so fail before the run, not after.
- **Explicit over implicit.** No hidden magic — prefer dotted class paths over string aliases, declared wiring over inferred, concrete config over convention. If behavior depends on a value, make that value explicit. Prefer explicit arguments over defaults; a default is justified only when it is the overwhelmingly common case or genuinely optional.
- **One source of truth.** A given fact — a dimension, a learning rate, a version — lives in exactly one place; everything else derives from it. Don't duplicate it where copies can drift. Tests may spell out expected values when doing so makes behavior explicit and guards against regressions.
- **Keep config declarative; compute in code.** Config holds data, not logic. Non-trivial or cross-referencing math belongs in a Python function — visible, testable — not spread across config interpolation or `eval`. Simple local derivations are fine.
- **No speculative generality.** Solve the problem in front of you. Don't add parameters, abstractions, extension points, or config for hypothetical futures — add them when a real caller needs them.
- **Smallest change that does the job.** Keep diffs focused and reviewable. Don't refactor, rename, move, or reformat unrelated code.
- **Match the surrounding code.** New code should read like the code around it — match its structure, comment density, and idioms. Name things descriptively: say what the value holds, avoid cryptic `tmp` / `data2` names. Short math/loop names (`q`, `i`, `x`) are fine when conventional and local. Consistency beats personal preference.
- **Reuse and extend, don't reinvent.** Before adding code, look for an existing function, utility, or pattern to reuse or extend. Add a new case in the shape of its siblings rather than a parallel one-off path, and call existing helpers instead of reimplementing them.
- **Comments say why, not what.** The code shows what it does; comments capture intent, trade-offs, and non-obvious constraints. Keep them concise; don't narrate the obvious.

## Communication

Talk with relevant context and minimal technical jargon.
Lead with what a thing does and why it matters; introduce a term only when it earns its place, and briefly say what it means.
Prefer a plain explanation a new maintainer could follow over dense insider shorthand.
